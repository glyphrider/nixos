# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this repo is

A NixOS flake configuration serving three hosts, `stealth` (desktop), `nixie` (laptop), and `beast` (desktop) — all Hyprland desktops on AMD GPUs, built from the same shared `configuration.nix`/`home.nix` via a `mkHost` helper in `flake.nix`. `beast` is similar to `stealth` but with an upgraded CPU/memory/GPU. There is no application code, build system, or test suite — this is declarative system + home-manager configuration, and "correctness" means "the flake evaluates and each host's system activates cleanly."

## File layout

- `flake.nix` — flake inputs/outputs. Defines `mkHost` (takes `hostname` + `monitors`, wires up `configuration.nix`, `home.nix`, `home-manager`, and the per-host files below) and the three `nixosConfigurations` (`stealth`, `nixie`, `beast`) built from it. Pins several flake inputs.
- `configuration.nix` — shared system-level NixOS config for all hosts. See @claude-system.md.
- `home.nix` — shared home-manager config for user `brian`, used by all hosts. See @claude-home.md. Takes `monitors` (a list of Hyprland output names) as a module argument since that's the one shared-file value that varies per physical machine.
- `hosts/<name>/hardware-configuration.nix` — machine-generated by `nixos-generate-config`; treat as read-only (do not hand-edit; regenerate instead if disk layout changes). Entirely different between hosts (stealth: plain btrfs; nixie: LUKS-encrypted btrfs with a separate `/boot`; beast: plain btrfs with a separate `/efi`, no LUKS).
- `hosts/<name>/configuration.nix` / `hosts/<name>/home.nix` — per-host overrides layered on top of the shared files above. Keep these empty (`{ }`) unless a setting is genuinely tied to one physical machine (e.g. stealth's Edifier-speaker auto-connect over Bluetooth, or beast's Edifier speakers over TOSLink instead) — don't let host-specific peripheral config leak into the shared files, and don't move something here just because it *could* vary; only when it actually needs to.
- `wallpapers/` — static image assets referenced from `home.nix`.
- `pictures/` — static image assets other than wallpapers (e.g. the SDDM login-screen avatar) referenced from `home.nix`.

## Commands

- Apply changes to the running system: `nixos-rebuild --sudo --flake .#<hostname> switch` (run from the repo root; `<hostname>` is `stealth`, `nixie`, or `beast` — matches the machine you're on). Do **not** use `sudo nixos-rebuild switch` — the flake needs to be pointed at explicitly.
- Check that the flake evaluates without switching: `nixos-rebuild --sudo --flake .#<hostname> build` or `nix flake check` (checks all hosts).
- Update all flake inputs: `nix flake update`. Update a single input: `nix flake lock --update-input <name>`.
- Format Nix files with `nixfmt` or `nixpkgs-fmt` if invoked explicitly; the repo has no enforced formatter/CI, so match the existing style in the file you're editing (2-space indent, attribute sets `{ ... }`).

## Pins to revisit

Two deliberate version pins are working around upstream regressions rather than expressing a real preference for the old version. Check these periodically and drop the pin once the condition is met — don't carry them forward out of habit once they're no longer needed.

- **`hyprland.url`** (`flake.nix`) — pinned to a pre-#16140 commit because that Hyprland change broke Waybar's `hyprland/workspaces` module. Unpin once Waybar supports address-based workspace identity (check for a Waybar release/changelog mentioning it, then bump and test on one host before rolling out to the rest).
- **`linux-firmware`** (`hosts/nixie/configuration.nix` overlay) — pinned to tag `20260810` because `20260910` broke DMCUB firmware load on nixie's Rembrandt/Radeon 680M GPU. Unpin once nixpkgs' `linux-firmware` moves past this regression (check `pkgs.linux-firmware.version` after a `nix flake update`, or watch for a fix/revert upstream) — see @claude-system.md for the full incident.

## General conventions

- **Comments explain the "why," not the "what."** Several config blocks carry multi-line comments documenting a specific hardware/software quirk that motivated the setting. When editing near these, read the comment first — the setting is almost always compensating for a specific bug, not a stylistic choice — and keep/update the comment if the reasoning changes.
- `system.stateVersion` / `home.stateVersion` (currently `"25.11"`) must not be bumped casually; it controls migration behavior across NixOS releases, not "what version to target."
- Hardcoded values that look like they should be variables (IPs, MAC addresses, extension IDs) are tied to a specific physical setup — for anything in the shared `configuration.nix`/`home.nix`, confirm whether a value is genuinely common to all hosts (like the NAS IP, which `stealth`, `nixie`, and `beast` all mount) or needs to move to `hosts/<name>/` before changing it.
